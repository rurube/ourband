# Phase 6 — 합주 일정과 세션 관리

현재 상태: **로컬 구현·검증 완료** 후 사용자 요청으로 GitHub Pages 배포에 포함했습니다. 사용자가 GitHub 배포만 선택해 운영 DB 권한 마이그레이션·원격 동시 수정 검증은 보류 상태입니다.

## 사용 방법

상단에서 밴드를 선택하고 **합주 관리 → 일정 등록**을 엽니다. 한국 날짜 기준 같은 밴드의 날짜당 일정 하나를 만들 수 있습니다. 곡 없이 날짜만 먼저 저장해도 됩니다.

곡 제목·가수로 검색해 희망곡을 추가합니다. **합주 확정곡에서 찾기**를 체크하면 확정곡을 고를 수 있습니다. 한 날짜에 같은 곡을 두 번 추가할 수 없으며 최대 100곡입니다. 곡별 펼침 영역에서 순서를 바꾸거나 이 날짜에서만 곡을 제외하고 메모를 작성합니다.

세션은 보컬·기타·베이스·드럼·건반입니다. 세션별 배정 추가를 여러 번 눌러 여러 명을 배정합니다. 밴드 멤버를 선택하거나 직접 닉네임을 입력할 수 있습니다. 같은 멤버를 서로 다른 세션에 배정하는 것은 허용하며 같은 세션의 중복 배정은 차단합니다. 곡별 메모는 Unicode 3000자, 직접 입력한 닉네임은 1~30자입니다. 곡당 배정 100개·일정 전체 500개로 제한합니다.

모든 구성원이 일정을 등록·수정·삭제할 수 있습니다. **삭제**는 날짜와 그 날짜의 합주곡·세션 배정을 삭제하며, 원본 희망곡·투표·댓글에는 영향을 주지 않습니다. 화면에서 삭제 내용 확인 체크 후 실행합니다.

합주 예정에는 오늘과 미래 일정을 가까운 날짜순으로, 지난 합주에는 오늘 이전 일정을 최근 날짜순으로 표시합니다. 날짜를 펼치면 곡 순서·메모·세션·YouTube 링크를 볼 수 있습니다. 목록은 6개씩 조회합니다. 한국 날짜가 바뀌거나 화면에 복귀하면 날짜 분류가 갱신됩니다.

예정 화면의 **합주 N회**는 해당 곡이 등록된 오늘 이전의 서로 다른 합주 날짜 수입니다. 오늘과 미래는 제외하며 곡 ID 기준이므로 제목을 바꿔도 유지됩니다. 과거 일정·곡을 삭제하면 다시 계산됩니다. 지난 합주 화면에는 횟수를 표시하지 않습니다.

저장 후 메인의 모든 밴드 일정과 희망곡의 합주 집계 캐시도 갱신합니다. 메인의 밴드별 **합주 관리** 링크는 해당 밴드를 선택하고 일정 화면으로 이동합니다. 합주 확정 상태는 날짜별 곡 배정과 별개입니다.

## 서버 계약

`20261105070000_rehearsal_management.sql`:

```text
save_rehearsal(p_date, p_tracks, p_id=null, p_expected=null) → rehearsal UUID
get_rehearsal_detail(p_id) → {id, rehearsal_date, updated_at, tracks:[...]}
delete_rehearsal(p_id, p_expected) → void
```

`p_tracks`는 다음 배열입니다. 배열 순서가 곡·세션 순서가 됩니다.

```json
[{
  "song_id": "existing-song-id",
  "notes": "곡별 메모",
  "sessions": [{
    "id": "기존 배정에만 포함하는 UUID",
    "session_type": "vocal",
    "member_id": "밴드 멤버 UUID 또는 null",
    "nickname_snapshot": "멤버일 때 서버가 실제 닉네임 확인, 게스트일 때 직접 입력"
  }]
}]
```

- 로그인한 계정의 실제 소속과 요청의 `x-band-id`를 서버에서 확인합니다. actor나 역할을 인자로 받지 않습니다.
- 모든 곡·멤버·기존 세션 ID가 해당 밴드·합주곡의 것인지 검증합니다. 다른 밴드에 소속돼 있더라도 선택한 밴드 밖의 데이터를 수정할 수 없습니다.
- 날짜를 잠근 후 `p_expected`와 DB의 `updated_at`을 비교합니다. 낡은 버전은 SQLSTATE `40001`로 거부합니다. 날짜·곡·메모·세션을 하나의 트랜잭션으로 저장하므로 후반 검증이 실패해도 앞부분을 포함해 전부 롤백합니다.
- 기존 곡 관계와 세션의 ID를 보존합니다. 변경하지 않은 배정은 기존 닉네임 스냅샷도 보존하며, 새 배정·변경한 배정은 그 밴드의 실제 닉네임을 캡처합니다.
- 두 멤버의 기존 세션을 서로 교환할 때 임시 UNIQUE 충돌이 나지 않도록 변경된 멤버 슬롯을 트랜잭션 안에서 정리한 후 적용합니다. 최종 `(rehearsal_song_id,session_type,member_id)` 중복은 DB 제약으로 차단합니다.
- `20261105070100_rehearsal_write_permissions.sql`은 회원의 테이블 직접 INSERT/UPDATE/DELETE 및 기존 열 단위 쓰기 권한을 회수합니다. SELECT·밴드 RLS는 유지하고, 회원의 모든 저장은 버전 검사를 하는 RPC를 통합니다. 신뢰된 service-role 유지보수는 별도입니다.
- 합주 횟수는 기록에서 계산하며 별도 집계 테이블을 만들지 않습니다. 상세 조회는 해당 밴드 데이터만 반환합니다.

## 화면 상태와 실패 처리

편집 초안은 열 때 한 번 만들고, 목록 재조회나 실패가 덮어쓰지 않습니다. 요청 중 중복 클릭과 편집을 잠그며 쓰기 요청을 자동 재시도하지 않습니다. 저장 결과가 불확실한 네트워크 오류에서는 목록으로 반영 여부를 확인하도록 안내합니다. 날짜 UNIQUE 제약도 재시도로 인한 중복 생성을 막습니다.

충돌하면 초안을 유지하고 안내합니다. **작성 내용 대신 최신 일정 불러오기**는 최신 데이터를 직접 확인해 새로 편집하려는 경우에만 누릅니다. 날짜·곡·배정 초안이 그 최신 값으로 대체됩니다.

조회 캐시는 밴드 ID로 구분합니다. 각 요청에 밴드 헤더를 고정하므로 편집 중 다른 밴드로 전환해도 저장 대상 밴드가 바뀌지 않습니다. 전체 밴드 일정, 해당 밴드의 일정·상세 및 곡 집계만 무효화합니다. 일정 전체를 15초마다 읽는 폴링이나 Realtime은 추가하지 않습니다. 실시간 변경 알림과 연결 실패 폴백은 Phase 7 범위입니다.

## 검증

```sh
npm run test:db
npm run test:rehearsals
npm run test:songs
npm run check:edge
npm run test:edge
npm run build
```

- 로컬 PostgreSQL 검증 **305개**: 기존 264개 + Phase 6 검증 41개
- 일정 입력·배정 초안 모델 검증 **4개**
- 기존 곡·투표·댓글 모델 9개와 인증 유틸리티 7개 유지
- 원격 통합 스크립트는 테스트 실행 때 생성한 QA 계정·밴드·곡·일정만 사용하며 마지막에 정리합니다. 기존 사용자의 데이터는 테스트에 사용하지 않습니다.
- 실제 원격 동시 편집 검증은 완료되지 않았습니다. 최초 실행에서 동시 저장 응답이 예상과 달라 오류 코드 진단을 추가했으며 후속 원격 검증·권한 마이그레이션 적용이 필요합니다.
- 최초 원격 시도 중 네트워크 권한 철회로 후속 검증이 중단됐으며, 이후 로컬 작업을 완료했고, 최신 요청에서는 사용자가 GitHub 배포만 선택했습니다. 브라우저 클릭·모바일 시각 검증도 미완료입니다.

추가 서버 비밀값·프런트 환경변수는 필요하지 않습니다. 원격에는 `20261105070000_rehearsal_management.sql`의 함수 추가까지만 적용됐습니다. `20261105070100_rehearsal_write_permissions.sql`은 로컬 파일만 준비된 상태이며 사이트 배포에는 Phase 6 프런트엔드를 포함했습니다. 이 상태는 원격 합주 기능 검증을 완료했다는 뜻이 아닙니다. 후속 원격 적용과 통합 검증이 필요합니다. Docker 환경의 pgTAP 래퍼는 `supabase/tests/database/rehearsals.test.sql`입니다.

## 일정 안에서 세션 바로 변경

합주 날짜를 펼치면 별도 수정 버튼 없이 각 곡의 세션을 바로 선택·추가·제거할 수 있습니다. **세션 저장**을 누르면 해당 곡의 배정만 반영합니다. 날짜·곡 선택·순서·메모 변경은 **날짜·곡 수정**에서 진행합니다. 멤버 선택지의 메인·가능 표시는 개인 포지션 설정을 사용합니다.

가장 가까운 예정 일정은 첫 페이지에서 항상 펼쳐져 있으며 접기 버튼을 표시하지 않습니다. 다른 일정을 펼쳐도 유지됩니다. 지난 합주와 나머지 일정은 기존 토글을 사용합니다.

세션 저장 전 최신 일정을 다시 읽어 날짜·메모·다른 곡의 변경을 유지한 채 해당 곡 세션만 합칩니다. 같은 곡의 배정이나 곡 관계가 변경·삭제·재생성됐으면 입력을 유지하고 충돌을 안내합니다. 최종 저장은 기존 버전 검증 RPC를 사용합니다. 저장 후 재조회만 실패한 경우에는 저장 완료를 안내하고 입력을 유지해 중복 저장을 막습니다. **작성 내용 대신 저장된 배정 불러오기**를 누르면 서버의 값으로 확인·초기화할 수 있습니다.

일정 모델 검증은 총 7개로 늘렸으며, 다른 곡·메모·순서 보존, 동일 곡의 충돌, 새 게스트 입력을 포함합니다. 운영 DB의 추가 변경·테스트 데이터 생성은 필요하지 않습니다.
